RSI適用案：敵対的レビュー
総合判定：条件付きで進めるべき

最大の問題は、評価器が存在することと、RSIの昇格判定に使える実績ラベルが30件以上存在することを混同している点である。

この部屋には評価能力も、設計変更の履歴も、失敗事例もある。しかし、それらがそのままRSIの学習データになるわけではない。

特に危険なのは、既存の成果物をRSIの構成要素に読み替えることで、まだ実装されていない機能まで「既にある」と認定してしまうことだ。

C1：フェーズBから開始できるか

VERDICT：不成立

理由：

71件のブリーフ、102件のラリー／設計、54件のDONEは活動量・成果物数であり、予測と実績が対になったラベル数ではない。

評価器が存在しても、事前予測・実測結果・予測対象・判定基準が同一単位で結合されていなければ較正データにはならない。

38.11→34.79mmの誤算などは有用な事例だが、現状の記述だけでは予測ログとして事前凍結されていたことを確認できない。したがって30件の実績ラベルがあるとは認定できない。

判定が変わる条件：

最低30件について、以下の対が確認できること。

実施前に凍結された予測（対象・数値・判定・確信度）。

対応する実測結果（同じ対象・測定方法・判定基準）。

予測と実績の照合結果、および結果を確定した証拠。

なお、30件は独立性・多様性・難易度の保証ではない。30件揃っても、同一種類の容易なジョブ30件なら一般化能力の証明にはならない。

追加攻撃：

ラベルの定義を曖昧にすると、次のような水増しが起きる。

1つの設計書に複数の主張があるため複数ラベルと数える。

1回のラリーで3席が判定したため3ラベルと数える。

1つの失敗を修正前・修正後・再確認で3ラベルと数える。

これらは独立した予測機会とは限らない。

30件という閾値を採用するなら、件数の数え方を先に固定すべきである。

C2：不足は予測ログだけか

VERDICT：不成立

理由：

失敗記録が散在している状態は、失敗台帳が存在する状態とは異なる。検索・分類・再利用・重複排除ができる保証がない。

設計書の版管理は、METHODの版管理と同一ではない。成果物の変更履歴と、意思決定手順・方法論の変更履歴は別の管理対象である。

最大の欠落は昇格判定の権限と責任である。誰が候補を作り、誰が評価し、誰が採用し、誰がロールバックするのかが定義されていない。

判定が変わる条件：

最低限、次の4つが実装・確認されること。

正規化された失敗台帳（原因・影響・再発条件・修正・再発有無）。

METHOD専用の版管理と変更差分。

昇格判定の実行者・承認者・拒否権の明文化。

METHOD変更と評価結果を結び付ける追跡可能な履歴。

追加攻撃：

特に危険なのは、METHODの版管理を単なる設計書の版管理で代用することだ。

例えば、設計書がv1からv2に変わったとしても、何がMETHODの変更で、何が物理モデルの変更で、何が単なる数値修正なのか区別できなければ、RSIは何を改善したのか測れない。

さらに、同じMETHODの版で複数の設計変更が行われた場合、結果が良くなってもMETHODの効果とは特定できない。

これは学習ループの帰属問題である。

C3：METHODだけを編集対象にすれば安全か

VERDICT：条件付き

理由：

編集対象を限定することは必要だが、編集対象の境界と実際の影響範囲は一致しない。

検証順序、検証粒度、サンプル選択、再試行回数、停止条件をMETHODから変更すれば、物理ゲートを一切編集せずに実質的な合格率を操作できる。

したがって、ゲートのコードや採点基準を保護するだけでは、評価の完全性は守れない。

具体的な迂回経路：

METHOD側の変更 / 実質的な危険

検証順序の変更 / 失敗しやすい検証を後回しにする

検証粒度の変更 / 厳しいケースを粗い検査で代替する

対象選択の変更 / 成功しやすいケースだけを評価する

再試行回数の変更 / 失敗を繰り返して成功結果だけを残す

停止条件の変更 / 未解決の失敗を残したまま完了扱いにする

ラリーへの提出情報の変更 / 各席の判断に必要な情報を欠落させる

結果の集約方法の変更 / 不一致や少数意見を見えなくする

例えば、等価性ゲートがビット一致を要求していても、ビット一致を確認する対象をMETHODが選べるなら、ゲート自体は改変されていないのに合格が容易になる。

これは明確な抜け道である。

判定が変わる条件：

METHODに対して、以下の不変条件を設けること。

ゲートの実行対象・実行回数・順序・停止条件を保護する。

評価対象の選択と除外を記録する。

再試行と失敗の履歴を全件保存する。

METHOD変更の前後で同一の固定テストセットを実行する。

物理ゲートとラリーの基準を変更する権限をRSIに与えない。

さらに、変更後のMETHODがゲートを迂回できないことを、独立した監査手順で確認する必要がある。

C4：既存物との対応づけは正しいか

VERDICT：条件付き

理由：

METHOD版アーカイブ≒設計書の版管理という対応は、設計成果物の履歴という点では部分的に正しいが、方法論の変更履歴まで保証しない。

失敗台帳≒レポートに散在する失敗記録という対応は、記録が存在するという意味では正しいが、台帳としての検索性・構造化・再利用性を満たさない。

段の順序が固定されていても、各段の入力・出力・責任・変更権限が固定されているとは限らない。

具体的な対応関係の破綻：

RSIの構成要素 / 既存物 / 破綻点

METHODアーカイブ / 設計書の版管理 / 方法の変更と成果物の変更が混在

失敗台帳 / 各レポートの失敗記録 / 横断検索・分類・再発追跡がない

昇格判定 / 本人の採用判断 / 判断の一貫性・再現性が保証されない

評価器 / 物理ゲート・AIラリー / 方法の予測精度を測る評価器とは別物

学習データ / DONE台帳 / DONEは予測の正しさを意味しない

特に注意すべきは、本人の採用判断をそのまま昇格ラベルとみなすことだ。

本人が採用した設計が後に失敗する可能性もある。反対に、本人が保留した設計が後に正しいと分かる可能性もある。

採用・不採用は意思決定の結果であり、方法の性能を直接示す真値ではない。

判定が変わる条件：

既存ファイルを実際に横断して、METHOD変更・失敗・予測・実績・採用判断が一意のIDで結合できることを示す。さらに、各対応関係の欠落率を測定すること。

C5：RSIは過剰設計ではないか

VERDICT：条件付き

理由：

現行体制には既に物理ゲート、複数AIによる敵対的レビュー、継続台帳、本人の最終判断があり、設計品質を維持・改善する仕組みは存在する。

RSIを追加すると、予測記録、失敗の正規化、METHODの差分管理、昇格判定、監査という新たな運用コストが発生する。

それらが現行体制では発見・修正できなかった失敗を追加的に減らす証拠がない段階では、RSIは改善装置ではなく管理装置の追加に終わる可能性が高い。

最も強い反論：

「この部屋は既に自己改善している。失敗はラリーで発見され、設計書が修正され、確認ラリーで検証され、本人が採用を判断している。しかも継続台帳の54/59がDONEである。ここにRSIを重ねても、同じ問題を別の記録形式で管理するだけではないか。予測ログがないことは、現行の改善能力が不足している証拠ではない。RSIの導入によって改善速度が上がる、再発が減る、判断精度が上がるという比較実測がない以上、追加の仕組みは機会費用を生む。特に開発プロジェクトの本来の目的は物理的に正しい水面コースティクスを完成させることであり、改善システム自体を開発することではない。」

この反論は強い。

また、現行方式にはRSIが持たない利点がある。複数AIによる異なる視点の攻撃と、本人の物理的な判断が直接結びついていることだ。これを形式化しすぎると、実際の問題発見よりも記録の整合性を優先する逆転が起きる。

判定が変わる条件：

小規模な比較試験で、RSI導入前後の以下を比較すること。

同種の失敗の再発率

予測誤差

問題発見から修正確定までの時間

人間のレビュー負荷

追加運用時間

RSIありの方が、追加コストを含めても改善するという実測が必要。

総合判定
条件付きで進めるべき

最大の理由：この部屋にはRSIを動かすための評価能力と改善履歴はあるが、フェーズBを成立させる「事前凍結された予測と実績の対応ラベル30件」があるとは証明されていない。

最も危険な設計上の誤認

今回の案には、3つの異なる成熟度が混在している。

評価能力の成熟：物理ゲート・複数AIラリーが存在する。

改善履歴の成熟：設計変更・失敗・本人判断が蓄積している。

学習データの成熟：事前予測と実績が結合されたラベルが存在する。

1と2が成熟していることから、3も成熟しているとは推論できない。

ここを混同したままフェーズBを開始すると、RSIは過去の成功・失敗を後付けで解釈し、METHODの優劣を誤判定する。

私が要求する最小の修正

フェーズBを名乗る前に、次の段階を挟むべきである。

段階 / 実施内容 / 昇格

B0 / METHODの境界・権限・不変条件を定義 / 無効

B1 / 予測ログを導入し、前向きに記録 / 無効

B2 / 30件以上の対応済みラベルを蓄積 / 無効

B3 / ラベルの質・独立性・欠落率を監査 / 条件付き有効化

B4 / 固定テストセットでMETHOD変更を比較 / 限定的に有効化

重要なのは、30件に到達しただけで自動的に昇格判定を有効化しないこと。

30件は開始条件の一つであって、学習可能性の証明ではない。

そして、最初にRSIに与える権限は、METHODの変更提案までに限定する。採用・昇格・ロールバックは本人が行う。

この条件ならRSIの導入実験には合理性がある。しかし、現状の証拠だけで「最適な適用先」「フェーズBから開始可能」と認定することはできない。
