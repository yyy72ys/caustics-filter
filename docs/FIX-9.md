# FIX-9: スプラットを「点」から「面（クワッド）」へ＋深度マッピングの是正

対象: `caustics-filter/web/`（app.js / shader.js / env.js）
前提: 前方スプラッティングの枠組み（環境→水面状態→着地点→蓄積→HDR合成）は維持。パターン描画への回帰は禁止。

## 実ブラウザ目視判定（メイン側、FIX-7/FIX-8 拡大比較つき）
- FIX-8（GRID 384化）の拡大像は FIX-7 とほぼ同一だった。解像度を上げても構造が変わらない＝ボトルネックは解像度ではない。
- 全プリセット共通の残存問題: 明部が**孤立した点の集合**のままで、面にならない。フィラメント（連続した線）も立たない。

## 根本原因（2つ、コードで確認すること）
1. **GL_POINTS の点スプライト描画**: 現行は頂点ごとに独立したガウス点を打つだけなので、隣接セル同士の光が連続しない。Evan Wallace 方式の本質は「水面メッシュの三角形を着地点空間へ投影し、その面積で割る（面積比）」こと — つまり面のラスタライズ。点の蓄積では、セルの内部が埋まらず、折り畳みの重なりも三角形単位で数えられない。
2. **深度マッピングの歪み（疑い・要検証）**: レシピの水深ノード（m）と、シェーダ内の着地点変位スケール（P_SCALE / refract / dgL の積）の対応が物理的でない可能性。浅瀬プリセットで変位が小さすぎ／大きすぎると、折り畳みのスケールが実在の網目（画面幅の 1/20〜1/5 程度のセル）と一致しない。CPUミラーで「プリセット1・5 の着地点変位の標準偏差（画面幅比）」を測り、0.02〜0.15 の範囲に入っているか確認すること。外れていれば変位スケールを是正する（これは露出調整ではなく物理量の較正として RESULT.md に根拠を書く）。

## 変更指示
1. **クワッド（三角形）スプラットへの置換**: GL_POINTS を廃し、水面グリッドの各セルを2三角形で着地点空間に描くインデックス付きメッシュに変える。各頂点は着地点座標を持ち、フラグメントは四角形の面積比（水面側面積/底面側面積、頂点シェーダで計算し varying で渡す、またはフラグメントで dFdx/dFdy から面積を出す Evan 方式のどちらか）を輝度として加算する。セルの内部まで光が連続して分布し、重なったセル同士で自然に明るくなること。
   - メッシュ解像度は GRID 256 を既定（三角形 約13万）。性能が厳しければ 192 に落としてよいが、点描画には戻さない。
   - フットプリント的な柔らかさは、三角形の面積比そのもの＋バッファ解像度（現行 1024 上限）で得る。追加のガウスぼかしは最小限（現行の合成段の太陽ぼかしは維持）。
2. **深度マッピングの較正**: 上記「要検証」を実施し、変位スケールを全プリセットで画面幅比の標準偏差 0.02〜0.15 に収める。プリセットごとの水深ノード値（m）は不変。較正は dgL/refract の物理的再定義として一箇所で行い、プリセット別の場当たり調整はしない。
3. 検証追加: verify-node.js に (a) 変位標準偏差（画面幅比）の全プリセット値 (b) 密度マップの「明部連結性」指標（閾値1.5超の画素について、孤立点率＝隣接8方向に同閾値超の画素がない割合）を追加。目標: 孤立点率が FIX-8 ミラー比で半減以下。
4. 既存の数値目標は維持（平均1±0.15、min≤0.5、max 6〜12、相関は FIX-6 水準以上）。8秒ループ一致も維持。
5. スマホ性能: 三角形メッシュ化で頂点処理は増えるがフラグメントは軽くなる想定。frameCount 検証が通ること。60fps 実機確認は引き続きメイン側の残課題として明記。

## 禁止事項（再掲）
- 点スプラットへの回帰（フォールバック分岐としても残さない。後方ヤコビアンのフォールバックは従来どおり別に保持可）。
- 水の状態と無関係な模様生成。白の加算合成（最終段）。露出でのごまかし。
