## 機構への接続（全体像）
9件はバラバラの話題に見えて、実は1つの制作機構の部品になっている：

- **進め方の背骨**（@shion_takk）： 調査→要件定義→観点リスト→物理関係の全件チェック→1要素ずつ修正→手順の資産化。
- **合否の物差し**（@MengTo の scoring system ＋ @LexnLin の "Measured, not eyeballed"）： パーツ別に採点し、下限未満を直す。目視でなく測る。
- **工程の器**（@LexnLin escapement）： BRIEF＋shotlist の先行固定、builder／director の分業、反復ログのファイル化。
- **構造の正しさの外部裏付け**（@taziku_co／Higgsfield Miracle）： レイヤー分離＋奥行き保持が、映像制作の産業側でも自動化の主戦場になっている。
- **弱点の逃げ道**（@shion_takk と @MengTo が独立に同じ結論）： 有機的な複雑形状はコードモデリングの苦手領域で、メッシュ生成AI（Tripo／Meshy／Hi3D）で補うのが両者の定石。

## (A) 蛾モデリング proto3 への具体策

proto2 の残課題4点への処方。出典を併記する。進め方自体も処方に含む。

### A-0. 進め方（全課題に先立つ型）
1. **蛾そのものを先に調査する**（出典： shion_takk ③「対象の仕組みを調査させてから作り込む」、大全の「自己流をやめろ」）。エメラルドシャクガ類の形態 — 静止姿勢（翅を平らに広げ、腹部は後翅内縁の下に隠れる）、前翅・後翅の重なり順、翅の三角形状、鱗粉の見え方 — を調べ、**観点リスト**（The Twist 作例の「40の観点」に倣い、蛾版は10〜15観点でよい）にしてから build_moth.py を触る。
2. **参照写真の読み取りを言語化させる**（大全 第3章）： 写真から何を読み取ったか（輪郭・色・重なり）を先に文章で出させ、こちらの意図と突き合わせてから生成する。
3. **パーツ別スコアで合否を決める**（出典： MengTo scoring system ＋ LexnLin の測定QC）。スコアカード＝翅輪郭／腹部・体の構造／翅面質感／接地の4枚。各8/10（または測定閾値）未満は次に進まない。試行回数の予算も先に決める。
4. **一度に変えるのは1要素**（大全 第3章）： 形→質感→光・影の順に分け、同時変更で「何が効いたか」を失わない。
5. **手順と反復ログを資産化**（大全 第3章＋escapement の notes/ 方式）： build_moth.py の変更ごとに観点とスコアを RESULT-PROTO3.md に残す。

### A-1. 腹部の構造（カプセルが翅の上に乗って見える）への処方
- **関係表を先に作る**（出典： shion_takk ①④「全オブジェクトの配置状態を整理し、物理法則を属性分けして全件調査」）。蛾版： 腹部＝後翅内縁の下に隠れる／胸部＝前翅基部の下／脚＝樹皮に接する／翅同士＝前翅が後翅の上に重なる、を表にして、ビルド後に全件チェックする。今のカプセル問題は「重なり順（z-order）が形状に反映されていない」ことが本質で、見た目の調整ではなく関係の再定義で直す。
- **重なりと沈み込みは専用オブジェクトで担保する**（出典： @KOSAKA_Jun の証言 — 重さが形状に反映されず、指摘すると AI がソファーのへこみ計算用コリジョンオブジェクトを用意した）。腹部が後翅に隠れる境界、翅が樹皮に接する面に、不可視のマスク／コリジョン形状を置き、「隠れる・接する」を構造で保証する。
- 実装イメージ： 腹部メッシュを後翅内縁の下に潜らせ、後翅の内縁側を腹部の上端に被せる。チェックは関係表との照合＋真上と斜めの2視点レンダーで「腹部が翅の上に独立して読めないこと」を確認。

### A-2. 翅の輪郭（写真より丸い）への処方
- **輪郭を数値で先に確定する**（出典： 大全の要件定義＋ escapement の BRIEF 先行固定）。写真のシルエットをトレースして頂点列（正規化座標）として持ち、生成はその輪郭から始める。「シャクガらしい三角形」は感覚でなく頂点列で固定する。
- **測って合否を出す**（出典： LexnLin exposure_check.py の型）。生成後にシルエット重なり率（写真シルエットとの IoU）と前翅の縦横比・角度を実測し、閾値未満なら輪郭だけを直す（A-0-4 の1要素原則）。
- スコアカード「翅輪郭」の項目に IoU をそのまま使う。

### A-3. 翅面の質感（クリーンすぎる／鱗粉感なし）への処方
- **テクスチャはシェーダーノードで作る**（出典： @KOSAKA_Jun の埴輪作例 — すごいテクスチャの正体はノード組みだった）。写真転写ではなく、ノードで鱗粉状の微細ノイズ＋斑＋色ムラ＋透けの不均一を生成する。proto2 の「帯」の手続き化を翅面全体に広げる形。
- ただし埴輪投稿への返信者の指摘「あの複雑さは要らない」も併記する。ノードは必要十分に（微細ノイズの粒度を鱗粉の実寸感に合わせる等、観点に紐づく分だけ）。
- **光と合成側でも詰める**（出典： @Yokohara_h — ライティングとフォグ／コンポジットの改善で質感が上がった実感）。鱗粉の見え方は角度依存の反射なので、マテリアルだけでなく光の当て方とコンポジットで最終調整する。工程は分ける（A-0-4）。

### A-4. 接地影（弱い）への処方
- **影の濃さでなく「接触の物理」で担保する**（出典： shion_takk ①の浮遊・貫入の全件チェック＋KOSAKA_Jun のコリジョン証言）。腹面と脚が樹皮面に接する高さに正しく置けているかを先に全件確認し、影は接触形状から作る（接触部ほど濃い AO 的な影を翅・胴の樹皮への投影として）。
- **測る**（出典： escapement の測定QC。proto2 で既に行った「影なし比較レンダーとの差分測定」を合否基準に格上げする： 接触帯の輝度低下量が閾値以上であること）。
- **実寸感の確認**（出典： @GOROman の AR 実寸チェック）。蛾の大きさを写真の樹皮の目の大きさと照らして検証する。接地の説得力はスケール感の正しさと一体。

### A-5. 逃げ道（判断はユーザーに残す）
- @shion_takk と @MengTo は独立に「有機的な複雑形状はコードモデリングの苦手領域で、メッシュ生成AI（Tripo／Meshy／Hi3D）で補う」に至っている。腹部＋翅の有機形状が A-1〜A-3 で届かない場合の選択肢として、写真からメッシュ生成して骨格（姿勢・アニメーション）だけコード側で持つ分担がありうる。
- ただしユーザーの原指示は「切り抜きでなく作る」であり、写真からの自動生成はその精神と衝突しうる。**採用可否はユーザーの判断事項**として明示し、勝手に切り替えない。
