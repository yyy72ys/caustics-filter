# FIX-8: スプラットの解像度不足の解消（前方方式は維持）

対象: `caustics-filter/web/`（app.js / shader.js）
前提: FIX-7 の前方スプラッティング方式は正しい（実ブラウザで前進を確認）。変えるのは離散化の細かさだけ。方式・水状態・合成は不変。

## 実ブラウザ目視判定（メイン側、FIX-7）
- 前進: プリセット0で初めて、点同士が短い線片として繋がる兆しが出た（FIX-6 との拡大比較で確認）。プリセット1は自然で破綻なし。
- 残存問題は1つに絞れた: **明るい塊のスケールがスプラット格子（GRID 192）のセルと同じ大きさ**で、構造が「格子の粒」に支配されている。リファレンスの網目はこの数倍〜十倍のスケールのセルが主役。
- 副次的問題: スプラット頂点シェーダの `fwidth` が WebGL1 頂点シェーダで使えずコンパイルエラー（フォールバック動作はしているが、意図したコードではないので除去・置換すること）。

## 物理的な裏付け
- プリセット1（緑の川の浅瀬）は実効水深が浅く、着地点の変位＝勾配×水深 が小さい。変位がスプラット格子間隔未満だと面積比≈1一様になり、網目が立たない（現にプリセット1がほぼ無模様）。変位が格子間隔の数倍になる解像度まで上げれば、浅瀬でも折り畳みが解像度内に現れる。

## 変更指示
1. **GRID 引き上げ**: 192 → 384（頂点数 約4倍、147k点）。重ければ 320 でも可だが、狙いは「浅瀬プリセットの着地点変位が格子間隔の3倍以上」になること。verify-node の CPU ミラーでプリセット1の変位/格子間隔比を算出し、3以上であることを確認して RESULT.md に記録する。
2. **バッファ解像度**: 上限 512 → 1024（描画解像度と同等まで可）。フットプリント半径の下限は現行式を維持（格子が細くなった分、相対的には自動で細かくなる）。
3. **fwidth 問題の除去**: 頂点シェーダ内の fwidth 使用箇所を、フラグメント側での計算か定数式に置換し、コンパイルエラーをゼロにする（verify-web のシェーダーコンパイル行に FAIL が出ないこと）。
4. **性能の担保**: GL_POINTS 数増加に伴う負荷を app.js 側で計測できるよう、既存の frameCount 検証が通ること（verify-web/moth が OVERALL OK）。スマホ実機 60fps の最終確認はメイン側の残課題として RESULT.md に明記（過剰な間引きはしない）。
5. プリセット値・UI・スキーマ不変。kc 等の再較正は不要（解像度の変更のみで見えが変わるはず）。

## 完了条件
- node --check 全JS OK、verify-node.js 全項目 PASS（変位/格子間隔比の新規項目を含む）。
- RESULT.md に FIX-8 節（GRID/バッファ値、プリセット1の変位比、fwidth 解消の方法）、STATUS.md に完了記録。
- ブラウザ実測はメイン側が行う。ブロッカーは STATUS.md に記録し、可能な範囲を完了させる。
