# BRIEF-V4-1-17 — サブ枠 2048² 本走（高速堆積法で C 水準の格子決着）

Workdir: `D:\yohey2026\dsh\muse\caustics-filter\offline`
前任: v4-1-16（REPORT-V4-1-16.md / numbers-v4-1-16.json、out/v4-1-16/）。本ジョブはその続き。

## 目的

深さ 4.0 m のサブ枠について、C 統計（std・p99）が格子を細かくすると収束するかを 2048² で決着させる。
既知の事実（v4-1-15 / v4-1-16 実測）: 512²→1024² で std −31.68% / p99 −25.64%（48フレーム平均、15% 基準で 0/48）＝未収束。
本ジョブの問いは「2048² vs 1024² が 15% 以内に入るか」。

## 手法（固定）

- 堆積は `transport_mesh_fast.py`（v4-1-16 で新設、verbatim とビット一致を実証済み）をそのまま使う。**既存 .py は1バイトも変えない**。新規ファイルはドライバ `run_v4_1_17.py` のみ可。
- 条件は v4-1-16 STAGE 3 と同一、格子だけ N_s = 2048 に変える:
  - 窓 4.8000 × 3.5217 m、深さ 4.0 m、プリセット5（U = 6 m/s, F = 100 m、シード 3255045276382562994）
  - フレーム格子 736×540、フレーム 0〜47（48本、時刻は run_v4_1_16.py の STAGE 3 と同じ割り付け）
  - `BOX_BULK_MAX = 1<<20`
  - 場の組み立ては `build_scene('sub', n=2048)` 相当（run_v4_1_15.py の import を読み取りのみで使う、v4-1-16 と同じ型）
- 並列はフレーム単位のみ。開始前に空きメモリを実測し、1プロセス約 500 MB（2048² の外挿、未実測）を前提に、総使用量が空きの約70%を超えないワーカー数を選ぶ（物理コア 6 が既定、上限 8）。選んだ数と根拠を numbers に記録する。メモリ不足で落ちたらワーカー数を下げて再開してよい（フレーム単位で冪等に：済んだフレームは飛ばす）。
- 出力は C 層の統計のみ。PNG/MP4 は作らない。

## 記録（必須）

- `out/v4-1-17/run-v4-1-17.log` に進捗を逐次書く（開始行、ワーカー数、フレーム完了ごとに行、終了行）。監視がこのファイルを読む。
- フレームごと: C の mean/std/min/max/p01/p50/p99、エネルギー会計 rel_err、実時間。
- 比較（G-CONV の定義は v4-1.15 と同じ 15% 基準、フレームごと）:
  - 主: 2048² vs 1024²（相手は out/v4-1-16/numbers-v4-1-16.json の stage3、48フレーム）
  - 副: 2048² vs 512²（相手は v4-1-15 の基準 48フレーム、numbers-v4-1-16.json の gconv_vs_512 が持つ 512² 側統計を使ってよい）
  - それぞれ std・p99 の相対差の平均と範囲、15% 以内のフレーム数を出す。
