## 2. 前提 [E] — Smith shadow 監査：**KEEP（維持）**

- コード上の事実（`numbers-v8.json → prerequisite_tasks.smith_shadow_audit.code_facts`）:
  - `det.py det_frame` は全ての前像を構造的に加算するが、**遮蔽判定が一切ない**（`xb = mod(Psx + Tx*t, S)` にレイ同士の衝突・水平線テストなし）。
  - エネルギー分母 `total_rays / N_buf²` は解析値で、バッファは再スケールされない → 遮蔽によるエネルギー欠落は原理的に出ない。
  - `transport.py photon_frame` も同じ単一バウンス写像で、同じ省略を共有（det.py 固有のバグではない）。
  - `v5_physics.smith_g1_beckmann`: α·tanθ ≥ 1/1.6 で Λ=0, **G1 = 1 厳密**。
- 判定: **二重計上なし**（輸送は「集光（ヤコビアン和）」、G1 は「可視性（統計的マスキング）」で物理が直交）。削除すると低太陽・強風の隅で物理的に明るすぎる像になるため維持。
- 参照シーンでの実測: G1(v33) = 1.0、G1(v8) = 1.0（いずれも厳密に 1.0、rms_slope 0.1085 / 0.1488、太陽高度 59.03°、a = 15.35）→ **ノードを外してもスチル差は 0**。隅の表（抜粋）: rms_slope 0.1085 で高度 5° → G1 = 0.9462、3° → G1 = 0.8206（rms_slope 0.05 では 5° で 1.0、3° で 0.9814）。つまり G1 は「低太陽・陡波」の隅でのみ効き、そこは輸送の遮蔽欠落が最も悪い隅と一致する（補完関係）。

## 4. 前提 [M] — フォトン検算＋MS-SSIM 分解：**スカラーゲートは未達、分解は「ノイズ支配」**

条件は v2 検算と同一（4,000,000 フォトン、2048²、同じ σ=0.75 px ピクセルフィルタ、同じ複合）。平均は解析期待値と 1e-12 で一致（R/G/B = 0.6064565977 / 0.5882628998 / 0.5579400699）。

| 指標 | 値 | 判定 |
|---|---|---|
| MS-SSIM(log1pC) det vs photon | **0.2853** | **未達**（ゲート 0.90） |
| スチル MS-SSIM(グレー) det vs photon | **0.99618** | 実質一致 |
| スチル内のコースティク・ピーク位置差 | **0 px**（0 mm） | 一致 |
| スチル内ピーク高輝度の相対差 | 0.24 % | 一致 |
| スチルの平均絶対差 | 1.28 / 255 | 一致 |
| C の p50 / p99 / p99.9 相対差 | 1.09 % / 23.2 % / 26.1 % | 光子場が裾で重い |
| ピーク位置（xcorr、平滑 3 px） | **4 px = 2.9 mm** | コースティク scale に対し小 |
| 生 argmax 位置差 | 1115 px | 単一ノイズ画素が所有（参考値） |
| 自己相関 FWHM | det 149.8 px / photon 38.0 px | 光子場に白色成分 |

**解釈（反証可能な形で）**: 4M フォトンは 2048² で **0.95 光子/マスター画素**。v8 状態の C は v2 のそれより裾が軽い（本マスター p99 = 1.509、v2 マスターは p99 = 4.28）ため、同じ光子数でも構造に対するショットノイズ比が悪い。平均は完全一致・p50 は 1 % 一致で、**裾だけが上下対称に膨らむ**（photon min 0.0235 vs det 0.6276、max 3.81 vs 2.10）＝ バイアスではなく Poisson ノイズ。

補助診断（**ゲートではない**、`photon-16M-diagnostic.json`）: 同一場を 16M フォトン（3.81 光子/画素）で再実行すると MS-SSIM = **0.4627**（4M の 0.2853 から上昇、ただし 16M vs 4M は 0.5698）。p99 相対差は 8.59 % に低下。**光子を 4 倍にしても 0.9 には届かない**ため、「光子数を増やせば通る」とは主張しない。

参考: v2 の同条件検算も MS-SSIM 0.8274 で自ゲート 0.9 を満たしていない（`out/v2/numbers-v2.json photon_check.pass=false`）。つまりこのゲートは**フル解像度では元々厳しい**。本報告では (a) スカラーゲートは未達、(b) 分解すると差はピーク位置ではなく光子ノイズ、(c)  deliverables（スチル）は 0.996 で一致、を分離して提示する。**「輸送モデルが合っていない」という主張は、この数値からは支持されない。**

## 6. 正直な限界・反証（主張を弱める事実）

1. **ゲート 4 の realised H_s は上限超過**: クランプはスペクトル H_s に掛かる。単一スナップショットの実現値は shallow 0.08473、clamp 0.08500 で、0.78h = 0.0780 を **+8.6 % / +9.0 %** 上回る。「実現した波高が 0.78h を超えない」という強い主張は**できない**。ゲートの定義（有効 H / スペクトル H_s）に対しては PASS。
2. **ゲート 2 の as-used は 4.16 % 低い**: 8 s ループ量子化により、実装が実際に進める位相速度は理論の 0.9585 倍。連続分散の式は 1.000067 で一致するが、シミュレーションの実効速度はそうではない。
3. **前提 [M] のスカラーゲートは未達**（0.2853 < 0.9）。16M でも 0.4627。光子密度を上げても通らないため「ノイズだから無視してよい」とは書かない。輸送の一致を示すのは (a) 平均の 1e-12 一致、(b) スチル MS-SSIM 0.996、(c) ピーク位置 xcorr 2.9 mm、(d) 裾の対称な膨らみ、までである。
4. **ゲート 1 の寄与シェアは解像度依存**（スモーク 60 % → フル 97 %）。「差分の 97 % はアンカー」はこの帯域での話で、一般則ではない。
5. **アンカーのモデル選択は較正**（JONSWAP/Donelan の中央値則、Ft=436 は fit 範囲 1e3–1e5 の外挿）。数値の不確かさは `anchor.sensitivity` に全部入っているが、外挿の方向の誤差は補正していない。
6. **mean(C) の 2 つの値**: 1.0000003576 は float32 pairwise 和（ログが印字した値）、0.99999999999 は float64 和。差 3.6e-7 は**累積器の差**で場の差ではない（`numbers-v8.json → numerics_notes`）。
7. **単位ラベルの誤り（既存コード）**: `v8_prereq.peak_shift` の `*_mm` は実際には「メートル/マスター画素 × px」＝**メートル**。本報告では物理量に直して mm で書いた（例: xcorr 4 px = 0.00288 m = 2.9 mm）。JSON のキー名は既存のまま。
8. **死因は未確定**。OOM は仮説で、証拠は「トレースバック無し・プロセス消滅・同時刻の並行作業」。フォトン経路のピークは 675 MB だったので、同じ経路が再度落ちる可能性は低いが、保証はしない。

## 8. 再現手順

```
cd D:\yohey2026\dsh\muse\caustics-filter\offline
python run_v8_finish.py --verify-lowmem          # 光子経路の等価性（1.7 s）
python run_v8_finish.py --stages base            # E/Q/スチル（キャッシュがあれば skip）
python run_v8_finish.py --stages photon          # [M] 4M フォトン
python run_v8_finish.py --stages gates234        # ゲート 2/3/4
python run_v8_finish.py --stages gate1           # ゲート 1
python run_v8_finish.py --stages gates56         # ゲート 5/6
python run_v8_finish.py --stages gate6fix        # ゲート 6 の同一条件検証
python run_v8_finish.py --stages photon16m       # 補助診断（任意）
python run_v8_finish.py --stages assemble        # numbers/prereq/panel
```

`--force` を付けない限り、`_parts/` にキャッシュがあるステージは再計算しない。合計の計算時間は約 19 分（フォアグラウンド）。
